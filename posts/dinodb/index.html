Building DinoDB: a sharded, multi-threaded key-value store in C++

By Uday on August 26, 2026 · ~20 min read
c++ · systems · concurrency · networking

Why build another Redis

Redis's core trick is deceptively simple: run every command on a single thread. No locks, no races, no torn reads — the entire data structure engine gets to pretend concurrency doesn't exist, because from its point of view it doesn't. That buys enormous simplicity, and for years it was also fast enough, because a single core can push millions of simple operations per second and the network stack is usually the real bottleneck anyway.

But “fast enough” has a ceiling, and the ceiling is one core. If your workload is CPU-bound — big ZRANGE scans, large hash operations, many concurrent clients each doing real work — a single-threaded engine simply cannot use the seven other cores sitting idle next to it. Redis's own answer, over the years, has been to lean on clustering (shard across processes, not threads) rather than take on internal concurrency.

DinoDB asks a narrower question: what does an in-memory KV store look like if you do let multiple threads execute commands at once, and pay for that with real synchronization instead of getting it for free? Not lock-free, epoch-reclaimed, seqlock-validated concurrency — that's a different, much harder project — but the simplest thing that can plausibly work: partition the keyspace into shards, put a reader-writer lock on each one, and let unrelated keys never see each other's locks.

This post walks through how that's built, from the wire protocol up to the on-disk snapshot format. Source is on GitHub.

Design goals

  1. Speak RESP — redis-cli and any standard Redis client library should be able to talk to it with zero adaptation.
  2. Real parallelism, not the illusion of it — two clients touching two different keys should never wait on each other, on any code path.
  3. A codebase one person can hold in their head — every subsystem (parser, store, dispatcher, reactor, persistence) is small, has one job, and is unit-testable in isolation.
  4. Boring, portable primitives — std::shared_mutex, poll(), plain TCP sockets. No lock-free tricks, no platform-specific event APIs, no external dependencies beyond the C++ standard library.

Four layers, each one only aware of the layer directly below it:

  • Networking owns file descriptors and nothing else. One acceptor thread blocks on accept(); every new connection is handed to one of N worker threads round-robin. Each worker runs its own poll() loop over the connections it owns — no connection is ever touched by more than one thread, so the networking layer itself needs zero locks.
  • Protocol turns bytes into requests and replies back into bytes. It knows nothing about what a SET does.
  • Dispatch knows what every command does, but not how bytes got to it or where the store's locks live.
  • The sharded store is the only place a mutex is ever taken.

Each layer being ignorant of the ones above it is what makes the whole thing unit-testable without spinning up a socket — the test suite calls dispatch() directly against a Store and never touches the network at all.

The store: sharding instead of one big lock

The naive version of a thread-safe hash map is std::mutex plus std::unordered_map. It works, and it also means every single command — GET, SET, TTL, doesn't matter — serializes behind the same lock. At that point the extra worker threads are pure overhead: you've built a single-threaded database with more context-switching.

DinoDB instead fixes the shard count at 32 and hashes every key into exactly one of them:

class Shard {
public:
    std::shared_mutex mtx;
    std::unordered_map<std::string, Entry> map;
};

Shard& Store::shard_for(const std::string& key) {
    size_t h = hasher_(key);
    return *shards_[h % shards_.size()];
}

Every read (GET, HGET, TTL, ...) takes a shared_lock on exactly one shard; every write (SET, DEL, LPUSH, ...) takes a unique_lock on exactly one shard. Two clients hitting different shards never block each other — including two writers. Two clients hitting the same key still serialize, same as Redis's single global thread would, but now that's the exception, not the rule:

sequenceDiagram
    participant C1 as Client A: SET foo 1
    participant C2 as Client B: SET bar 2
    participant SF as Shard(foo)
    participant SB as Shard(bar)
    C1->>SF: unique_lock
    C2->>SB: unique_lock
    Note over SF,SB: Different shards -> no contention, run in parallel
    SF-->>C1: OK
    SB-->>C2: OK

With 32 shards and a reasonable hash distribution, two random keys land in the same shard about 1-in-32 of the time — contention drops roughly linearly with shard count, at the cost of 32 mutexes' worth of memory and a hash computation per lookup. That's the whole trade: DinoDB is choosing coarse, cheap, well-understood parallelism over fine-grained, expensive, hard-to-verify parallelism.

What actually lives in a shard

Rather than a tagged union of heap-allocated containers, every key maps to one fixed-layout Value struct big enough to hold any of the five supported types:

struct Value {
    ValueType type;                              // which field is "live"
    std::string str;                              // String
    std::unordered_map<std::string, std::string> hash;  // Hash
    std::deque<std::string> list;                  // List
    std::unordered_set<std::string> set;            // Set
    std::unordered_map<std::string, double> zscores; // ZSet: member -> score
    std::multimap<double, std::string> zorder;       // ZSet: score -> member
};

struct Entry {
    Value value;
    std::optional<std::chrono::system_clock::time_point> expires_at;
};

This is a deliberate simplification versus e.g. Redis's listpack/intset/embstr family of size-tuned encodings, or an epoch-reclaimed structure that hands back memory to other threads lazily. Every key here costs roughly sizeof(Value) regardless of whether it holds a 3-byte string or a 10,000-entry hash — noticeably more memory overhead per key, in exchange for an ownership model simple enough that there is no reclamation problem to solve at all: a std::unique_lock is held, the struct is mutated in place, the lock is released. No epochs, no hazard pointers, no deferred frees.

Sorted sets get two structures instead of one specifically so that ZRANGE (score-ordered) doesn't have to sort on every call: zscores answers “what's this member's score” in O(1), and zorder — a std::multimap<double, std::string> — keeps the score-sorted view maintained incrementally on every insert/update/remove:

void zset_put(const std::string& member, double score) {
    auto it = zscores.find(member);
    if (it != zscores.end()) {
        // erase the stale (old_score -> member) entry from zorder first
        auto range = zorder.equal_range(it->second);
        for (auto r = range.first; r != range.second; ++r)
            if (r->second == member) { zorder.erase(r); break; }
        it->second = score;
    } else {
        zscores.emplace(member, score);
    }
    zorder.emplace(score, member);
}

Lazy expiry

TTLs are not swept by a background thread. Every read path (get_mut, exists, ttl_seconds, ...) checks expires_at against now() under the shard's lock it already had to take anyway, and evicts the entry on the spot if it's stale:

Entry* Store::get_mut(const std::string& key) {
    Shard& s = shard_for(key);
    std::unique_lock lock(s.mtx);
    auto it = s.map.find(key);
    if (it == s.map.end()) return nullptr;
    if (it->second.expired(std::chrono::system_clock::now())) {
        s.map.erase(it);
        return nullptr;
    }
    return &it->second;
}

The cost is that a key nobody ever reads again outlives its TTL forever in memory. That's an acceptable trade for this project's scope — a background reaper thread is a natural next step, and it slots in cleanly because it would just call the same for_each used by KEYS and snapshotting.

The wire: a streaming RESP parser

Real Redis clients send RESP multibulk arrays — *3\r\n$3\r\nSET\r\n... — but the parser also accepts plain space-separated inline commands (PING\r\n), which makes manual testing with nc painless. TCP gives you a byte stream, not message boundaries, so the parser has to cope with a request arriving in pieces across multiple recv() calls, or multiple requests arriving in a single recv():

class Parser {
public:
    void feed(const char* data, size_t len);       // append raw bytes
    std::optional<Request> next();                  // pop one complete request, if any
private:
    std::string buf_;
    size_t pos_ = 0;   // parse cursor; buf_ is compacted periodically, not on every call
};

next() is the whole contract: call it in a loop after every feed(). If a complete request is sitting in the buffer it comes back immediately; if the buffer ends mid-length-prefix or mid-bulk-string, it returns nullopt and leaves pos_ untouched, so the next feed() picks up exactly where parsing left off. The buffer is only compacted (bytes before pos_ erased) once it's grown past a threshold, so a stream of small pipelined requests doesn't pay a memmove per request.

sequenceDiagram
    participant Sock as socket recv()
    participant Buf as Parser buffer
    participant Disp as dispatch()
    Sock->>Buf: feed(bytes) [partial: "*3\r\n$3\r\nSET\r\n$1"]
    Buf-->>Sock: next() -> nullopt (incomplete)
    Sock->>Buf: feed(bytes) [rest: "\r\nk\r\n$1\r\nv\r\n"]
    Buf-->>Disp: next() -> ["SET", "k", "v"]
    Disp-->>Buf: encoded reply appended to outbuf
    Buf-->>Sock: next() -> nullopt (buffer drained)

The reactor: one acceptor, N pollers, zero shared state per connection

DinoDB deliberately does not use epoll/kqueue/SO_REUSEPORT per-core fan-out the way high-end event-driven servers usually do. poll() is portable POSIX, present and identical on Linux and macOS, and simple enough to get right without conditionally-compiled platform code. The trade is a linear rescan of each worker's fd set every iteration instead of O(1) readiness notification — a real cost at very high connection counts, and a non-issue at the scale this project targets.

flowchart LR
    Client1((client)) -->|connect| Acceptor
    Client2((client)) -->|connect| Acceptor
    Client3((client)) -->|connect| Acceptor
    Acceptor["Acceptor thread\nblocking accept()"]
    Acceptor -->|fd, round-robin| Q0["Worker 0 pending queue"]
    Acceptor -->|fd, round-robin| Q1["Worker 1 pending queue"]
    Q0 --> P0["Worker 0: poll() over its own fds"]
    Q1 --> P1["Worker 1: poll() over its own fds"]

Ownership is the key invariant: once the acceptor hands a file descriptor to worker i's pending queue, only worker i ever calls recv(), send(), or close() on it. There is exactly one std::mutex in the entire networking layer — guarding each worker's pending-fd queue — and it's held only for the microseconds it takes to push or drain a std::deque<int>. No connection state is ever shared between threads, so the per-connection buffers (resp::Parser, the pending output bytes) don't need any synchronization at all.

Each worker's loop, per iteration:

  1. Drain its pending queue into its local connection map (new fds only).
  2. Build a pollfd list: POLLIN always, plus POLLOUT if that connection has unsent reply bytes buffered.
  3. poll() with a 200ms timeout — short enough that a newly-assigned connection is never invisible for long, long enough not to spin.
  4. For each ready fd: drain recv() until EAGAIN, feed every byte to that connection's parser, dispatch() every complete request that falls out, append the encoded reply to the connection's outbound buffer, then try to flush that buffer with send() (partial sends are just remembered and retried next iteration via POLLOUT).

Command dispatch

dispatch() is a flat, case-insensitive lookup over ~40 commands covering five data types plus key/server management. No command object graph, no visitor pattern — just a function that takes a Store& and a parsed request and returns an already-RESP-encoded reply string:

Every handler follows the same shape: validate argument count and types up front (returning a RESP error immediately if they're wrong), then take exactly one lock through the Store API, mutate, and encode a reply. No handler holds a lock across more than one store call, which is what makes the “one command touches one shard” invariant hold in practice and not just on paper.

ZRANGE's O(n) walk (rather than O(log n + k) via an order-statistics tree) and KEYS's full scan are the two honest weak points in the current design — both are correct and simple, neither is what a production KV store would ship.

Persistence: a snapshot format, not a log

DinoDB does not implement an append-only file. It has one persistence primitive — a full point-in-time snapshot — triggered by SAVE, a periodic autosave timer, and a save-on-clean-shutdown hook for SIGINT/SIGTERM. The format is a small custom length-prefixed binary layout, unrelated to Redis's RDB format:

flowchart TB
    H["Header\n'DINO' magic + version byte"]
    H --> E1["Entry: type byte, key, expiry flag [+ millis], payload"]
    E1 --> E2["Entry: type byte, key, expiry flag [+ millis], payload"]
    E2 --> Edots["... one entry per live key, across all 32 shards ..."]
    Edots --> EOF["EOF = end of entries"]

Each entry's payload shape depends on its type byte — a length-prefixed string for String, a count followed by key/value pairs for Hash, and so on for List/Set/ZSet. Writing is a single pass over Store::for_each, which takes each shard's lock just long enough to copy its live (non-expired) entries out — so a SAVE never blocks a command for longer than one shard's scan, and never blocks two shards at once.

Durability is via the standard write-temp-file, fsync, rename pattern: SAVE always writes to dinodb.rdb.tmp first and atomically renames it over dinodb.rdb only after every byte is flushed — a crash mid-write leaves the previous snapshot untouched rather than a half-written file.

Concurrency safety invariants

The whole locking story rests on a short list of invariants, each one enforced structurally rather than by convention:

  • A key belongs to exactly one shard, always, because shard_for(key) is a pure function of the key's hash — there is no code path where a key's shard changes over its lifetime.
  • No handler holds a lock across a call it doesn't own. Store's public API (get_mut, get_or_create, del, ...) takes and releases its shard lock internally per call; command handlers never reach into a Shard directly.
  • A connection's buffers are touched by exactly one thread. Once the acceptor enqueues an fd to worker i, no other worker ever sees that fd again, so resp::Parser and the per-connection output buffer need no synchronization of their own.
  • for_each (used by KEYS, SAVE, DBSIZE) takes a shared lock per shard, one shard at a time — never all 32 at once — so a full scan can't deadlock against, or starve, a concurrent single-key write on some other shard.

A concrete trace

Two clients, one SET, one GET, same key, arriving on different worker threads at roughly the same time:

sequenceDiagram
    participant CA as Client A (worker 0): SET user:1 alice
    participant CB as Client B (worker 3): GET user:1
    participant Sh as Shard(hash("user:1") % 32)

    CA->>Sh: unique_lock (write)
    CB->>Sh: shared_lock (write) -- blocks, waits for CA
    Sh-->>CA: entry created/updated, str="alice"
    CA->>Sh: unlock
    Sh-->>CB: lock acquired
    Sh-->>CB: read str="alice"
    CB->>Sh: unlock

Nothing here is DinoDB-specific — it's exactly what a std::shared_mutex guarantees. The interesting part is what doesn't happen: a third client doing SET other:key 1 on a different shard runs concurrently with both of these, untouched, on a third worker thread, the whole time.

Comparison with Redis

RedisDinoDB
LanguageCC++20
Command executionSingle-threaded event loop (one thread runs all commands, so no locking is needed); optional multi-threaded socket I/O since Redis 6Multi-threaded throughout: keys are sharded across 32 std::shared_mutex-guarded buckets, and commands on different shards run genuinely in parallel
I/O modelCustom ae event loop over epoll/kqueue/selectA dedicated acceptor thread round-robins new connections across a fixed worker pool, each worker running its own poll() loop

Replication / clusteringPrimary-replica, Sentinel, Redis ClusterNot implemented (single standalone process)

In short: Redis gets its safety from running commands on a single thread; DinoDB instead accepts real lock overhead in exchange for genuine multi-core parallelism on independent keys. Redis's feature set (scripting, replication, many more data types, tunable durability) is far broader — DinoDB is a much smaller project focused on the core KV/data-structure surface.

When this design is (and isn't) the right call

Use it whenReach for something else when
Workload is CPU-bound across many independent keysWorkload is dominated by a handful of hot keys — sharding doesn't help those
You want to reason about correctness with plain std::shared_mutex semanticsYou need to squeeze out the last 20% of throughput and can justify a lock-free design's audit cost
Memory headroom for a fixed-layout Value per key is fineKey count is huge and per-key overhead has to be minimized
A snapshot-based durability model is acceptableYou need Redis's AOF-level durability guarantees

What's not here yet

Pub/Sub, MULTI/EXEC transactions, Lua scripting, SCAN cursors, streams, bitmaps, HyperLogLog, geospatial commands, and any form of replication or clustering are all absent. Each is a reasonably self-contained addition given the existing layering — SCAN, for instance, is mostly a cursor wrapped around the same for_each that already powers KEYS.
